# Design of the REAPER RPKX reference extension

This document describes the host-integration design in
`examples/reaper_rpkx_extension/`. The extension is an **example built on top of
libreapeaks**, not a layer of the libreapeaks public API.

## Boundary between the library and the example

The reusable library owns REAPEAKS parsing, generation, strict REAPER-compatible
DSP, source-stamp types, and RPKX container support exposed by the root crate.
The example owns concerns that exist only because it is embedded in REAPER:

- `PCM_source` wrapping and provider registration;
- REAPER configuration/profile observation;
- scheduling peak-generation jobs from host callbacks and the main-thread timer;
- selecting raw media access versus REAPER's decoder;
- updating an existing `.reapeaks` file while an opaque RPKX suffix is present;
- host read/write exclusion, Windows rebuild-clear behavior, and crash recovery;
- diagnostic logging and fault injection used by the real-host tests.

Keeping these policies here prevents a REAPER-specific lifecycle from becoming a
requirement for applications that only need the `libreapeaks` library.

## High-level flow

```text
ordinary REAPER action
        │
        ▼
wrapped PCM_source (plugin.cpp)
        │
        ├─ observes requested peak profile / source lifecycle
        │
        ▼
Job (plugin_job.h)
        │
        ├─ canonical PCM16 WAVE ──► raw_pcm16_wave.h
        │                              │
        │                              └─ direct PCM16/streaming fast path
        │
        └─ other supported sources ─► REAPER PCM_source::GetSamples
                                       │
                                       ▼
                         Rust bridge / libreapeaks generator
                                       │
                                       ▼
                         generated standard REAPEAKS image
                                       │
                                       ▼
                         preserving store transaction
                                       │
                                       ├─ standard region replaced
                                       └─ existing RPKX suffix preserved
```

`bridge.h` is deliberately small. It is an internal C ABI between the C++ host
adapter and the Rust bridge crate, not a supported application ABI.

## Source wrapping

The extension registers a `PCM_source` provider. Supported sources are wrapped in
an object that delegates normal source behavior to REAPER while replacing the
peak-cache lifecycle with the preserving job path.

The wrapper registry is keyed by the exact `PCM_source*` base pointer. Public
example APIs such as the diagnostic/status helpers first look up that pointer;
they do not downcast arbitrary native sources. An unwrapped source is therefore
rejected rather than invoking undefined behavior.

Source/job identity includes the media path, source size/time stamp, requested
peak profile, and peak resolution. Jobs may be shared for the same identity, but
a rebuild or a changed source/profile must not accidentally reuse unrelated
work.

## Generation paths

### Canonical PCM16 WAVE

A strict, canonical PCM16 WAVE file can bypass REAPER's decoded-double path. The
example reads the little-endian PCM16 payload directly and feeds exactly those
integer samples into the same generator. This avoids the unnecessary
PCM16 -> double -> PCM16 round trip while preserving generated bytes.

Waveform generation uses a bounded streaming path so a long PCM16 file does not
require a whole-file PCM allocation. Spectral/spectrogram analysis may use the
batch path where the strict compatibility implementation requires it.

Files that do not satisfy the raw-reader conditions fall back to REAPER's
`PCM_source::GetSamples` path. The fast path is an optimization, not a change to
which bytes are accepted as correct.

### Strict spectral/spectrogram behavior

The bridge depends on the root `libreapeaks` crate with `strict-wdl`. FFT,
resampling, windowing, quantization, and layer layout therefore remain library
work. The reference extension should optimize data movement and scheduling
before changing those numerical operations, because byte identity with the
pinned REAPER oracle is an invariant.

## Preservation invariants

A preserving update must satisfy all of the following:

1. **Validate before mutation.** The new standard image and the existing cache
   structure are parsed before any destructive write.
2. **Preserve RPKX byte-for-byte.** Existing RPKX bytes are opaque to the standard
   peak rebuild and must compare exactly before/after.
3. **Reject stale identity by default.** A source-stamp mismatch is not permission
   to attach old extension data to new media.
4. **Do not reinterpret unknown suffixes.** Unknown trailing bytes are not treated
   as disposable standard data.
5. **Do not move a large suffix when the standard size is unchanged.** Same-size
   rebuilds overwrite the standard region in place and report zero tail bytes
   moved.
6. **Relocate only when required.** Standard grow/shrink operations move the
   suffix while preserving its exact bytes.
7. **Readers must not observe a half-written cache.** Read guards coordinate
   REAPER-facing cache reads with replacement/recovery.
8. **A failed regeneration must not silently fall back to a destructive native
   write.** Failure is surfaced and the pre-existing cache remains unchanged.

These are integration invariants, not optional performance tweaks.

## Redo/WAL durability

`src/store.rs` implements the example's preserving transaction and recovery
logic. The same-size fast path still uses a redo journal and durability barriers;
being fast is not permission to remove crash recovery.

The journal makes the intended standard-region replacement recoverable after a
process or machine interruption. Fault-injection tests exercise interruptions at
transaction boundaries and verify recovery to a valid complete cache rather
than accepting a torn state.

Performance logs separately report standard bytes written, RPKX tail bytes
moved, journal bytes written, and sync count. That separation is intentional: a
benchmark is not allowed to claim success by silently weakening durability.

## Read guards

`src/read_guard.rs` prevents a REAPER cache reader from opening a file while the
preserving writer/recovery path owns it. `GetPeakInfo` acquires the guard before
constructing or reusing REAPER's peak reader.

This is especially important because the extension is transparent: the host may
ask for display data while an ordinary rebuild is progressing.

## Windows guarded clear

REAPER's rebuild sequence has platform-specific file-lifecycle behavior on
Windows. `windows_guard.h` protects the existing cache across the host's clear
phase, detaches/restores the guarded copy as needed, and commits only after the
preserving replacement succeeds.

The guard belongs to this host example. Applications that do not run inside
REAPER should not inherit it merely because they use libreapeaks.

## Scheduling and concurrency

REAPER calls peak-build methods and also asks for peak display data. The example
keeps host-visible state in the wrapped source and advances deferred work from a
registered main-thread timer. Shared jobs prevent duplicate generation for an
identical source/profile.

Heavy generation may use worker threads, but REAPER callbacks and source
lifetime remain the authority for whether a job is still relevant. Job
completion distinguishes generated/ready work from simple cache reuse; a
`DONE reuse=1` record is never accepted by the tests as proof that regeneration
was exercised.

For waveform mode, the canonical PCM16 path can hand durability work to a reused
worker after peak data is ready. The real-host benchmark records peak-ready and
durable-ready times separately. The stronger durable state still has to complete
before the test accepts the transaction.

## Creation versus preservation

Glue, Render, and Record can create new media. At that moment there is no
pre-existing RPKX suffix, so “preservation” is not applicable to the initial
cache creation.

The preservation contract starts later:

```text
new media -> standard cache exists -> RPKX appended/created -> ordinary rebuild
                                                       │
                                                       └─ must preserve RPKX exactly
```

The host suite proves this lifecycle for Glue and Render. Live Record transport
is deliberately not a headless correctness dependency because it additionally
requires an available audio device. Once recorded media exists, its subsequent
PCM cache rebuild follows the same preservation path.

## Failure policy

The example prefers a visible failed peak job over corruption or destructive
fallback. Diagnostic builds can inject failure after generation; the host tests
require either:

- no cache is created when none existed, or
- the complete pre-existing cache SHA-256 remains identical.

That test is intentionally stronger than checking only the RPKX suffix.

## Non-goals

This reference implementation does not try to be:

- a stable libreapeaks API surface;
- a polished end-user REAPER product or installer;
- a compatibility layer for every REAPER release;
- a wrapper for arbitrary third-party `PCM_source` implementations;
- a replacement for REAPER's media decoders;
- a specification that requires applications to use this exact WAL, thread, or
  host-callback architecture.

The reusable contract is the library and documented file/API behavior. This
example exists to show one rigorously tested way to compose those pieces inside
REAPER 7.79.
