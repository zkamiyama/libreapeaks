# libreapeaks

**Use REAPER waveform-cache data outside REAPER.**

libreapeaks is a library for reading and generating REAPER `.reapeaks` files.
If you work with a DAW, the useful mental model is simple: `.reapeaks` is the
small analysis file REAPER uses to draw waveforms quickly. It is not the audio
itself, and libreapeaks never rewrites your source audio.

## Why an artist or DAW user might care

A custom sample browser, playback tool, editor, asset manager, or review app can
use libreapeaks to:

- open an existing REAPER waveform cache instead of re-analyzing the audio;
- draw smooth, deeply zoomable waveforms from the same multiresolution data;
- read REAPER spectral peak data for frequency-aware visualizations;
- generate compatible peak-cache data after decoding audio elsewhere;
- place a generated cache at a path selected by REAPER, so two applications can
  share one cache instead of maintaining separate waveform databases.

libreapeaks is **not** a REAPER plug-in, a DAW, or an audio codec pack. The core
works on decoded PCM. The reference players can use FFmpeg as an external
decoder.

## How close is it to REAPER?

For the conditions we continuously validate, very close: the Rust
`generate_pcm16_mode3` path with `strict-wdl` produces complete `.reapeaks`
files that are **byte-for-byte identical** to files generated by REAPER 7.79
x86_64 Linux. That comparison includes waveform, spectral, and `-'r'` loudness
layers, not just a visual approximation.

The current live oracle suite includes:

- 8 deterministic ALAC/M4A cases through REAPER's VIDEO/FFmpeg-backed source
  path, including silence, tones, steps, impulses, low-level signals, block-edge
  impulses, DC tails, and full-scale alternating samples;
- 16 adversarial whole-file cases covering 22.05, 32, 44.1, 48, 88.2, and
  96 kHz, `peakcachegenrs` values 150/300/500, mono/stereo/6-channel audio,
  EOF off-by-one boundaries, and 400 ms loudness-window boundaries;
- larger waveform and spectral corpora used to lock down quantization,
  resampling, FFT, spectral aggregation, and boundary behavior.

The float32 mode-3 writer uses the same recovered spectral/loudness machinery
and has separate waveform/spectral validation, but the two whole-file matrices
above are specifically PCM16 mode-3 tests.

This is a tested compatibility statement, **not** a claim that every REAPER
version, operating system, CPU architecture, codec, preference combination, or
possible floating-point input has been proven. See
[`docs/COMPATIBILITY.md`](docs/COMPATIBILITY.md) for the exact scope.

## Try the reference players

Build the Python extension first. The Python package enables `strict-wdl` by
default.

```bash
python -m pip install -U maturin
maturin develop --release
```

Desktop Qt player:

```bash
python -m pip install PySide6
python examples/pyside6_player.py /path/to/audio.wav
```

For a compressed source, explicitly use FFmpeg for cache generation:

```bash
python examples/pyside6_player.py song.flac --cache-decoder ffmpeg
```

Browser player:

```bash
python examples/web_player/server.py /path/to/audio.wav
# open http://127.0.0.1:8765/
```

Both demos use fixed-size waveform/spectral tiles and frontend LRUs, so panning
and zooming do not require a giant waveform texture. See
[`examples/PLAYER_DEMOS.md`](examples/PLAYER_DEMOS.md).

> **Current demo-generation scope:** the public Python generation functions used
> by the demos write waveform plus optional spectral layers. Complete REAPER
> mode-3 generation including loudness is currently exposed by the Rust
> `generate_pcm16_mode3` / `generate_f32_mode3` APIs. The C and Python writer
> APIs do not yet expose the mode-3 loudness path.

## What the library can read and generate

| Area | Current support |
|---|---|
| RPKN / RPKL waveform layers | Parse, generate, tile, render |
| RPKM | Header/layout recognition; compact waveform payload is not exposed through the current waveform pyramid |
| `-'s'` spectral peaks | Parse, generate, tile |
| `-'r'` loudness | Parse; generate through the Rust mode-3 API |
| `-'g'` spectrogram | Recognized/skipped by the parser; generation is not implemented |
| legacy `-'l'` loudness | Token recognized, payload layout not implemented |
| REAPER-style divisions | `default_divisions(sample_rate, peakcachegenrs)` in Rust/Python/C |
| GUI waveform pyramid | Native REAPER levels plus lazy ratio-4 display levels |
| C ABI | Parsing, view planning, waveform/spectral textures, rendering, waveform/spectral generation |
| Python | Parsing/GUI APIs and waveform/spectral generation |

## Build from Rust

Clone with the Cockos WDL submodule:

```bash
git clone --recurse-submodules https://github.com/zkamiyama/libreapeaks.git
cd libreapeaks
```

Normal Rust implementation:

```bash
cargo test
```

REAPER-oriented WDL backend used by the byte-exact compatibility gates:

```bash
cargo test --release --features strict-wdl
```

Rust generation entry points:

```text
generate_pcm16 / generate_f32
    waveform + optional spectral layers

generate_pcm16_mode3 / generate_f32_mode3
    waveform + spectral + loudness layers in REAPER 7.79 mode-3 order
```

## Python

The distribution name is `libreapeaks`; the import module is `reapeaks`.

```bash
maturin develop --release
python - <<'PY'
import reapeaks
print(reapeaks.default_divisions(48_000, 300))
PY
```

The result for 48 kHz / 300 peaks per second is:

```text
[160, 2400, 48000]
```

`300` is a preference, not a format constant. Applications that want to follow
a user's REAPER setup should use that setup's `peakcachegenrs` value or reuse
the positive divisions already stored in an existing cache.

## C / C++

Build the library and include `include/reapeaks.h`:

```bash
cargo build --release --features strict-wdl
```

The stable C ABI exposes file parsing, zoom planning, tiled waveform/spectral
textures, CPU RGBA rendering, REAPER-style division calculation, and PCM16/f32
waveform/spectral generation. Returned `RpkBuffer` objects must be released with
`rpk_buffer_free`.

See [`docs/C_ABI.md`](docs/C_ABI.md) for the exact current API surface and its
mode-3 limitation.

## Sharing REAPER's cache path

Generating correct bytes is only half of cache interoperability. REAPER also
chooses the **filename and directory** according to its active configuration.
Do not reverse-guess a central-cache filename from `altpeakspath`.

The canonical path oracle is REAPER's `GetPeakFileNameEx` API. libreapeaks ships
application-layer helpers that can:

1. read peak-related values from `reaper.ini`;
2. ask a short-lived REAPER process for the exact read/write path;
3. persist those answers in a cache map for later offline use.

The runnable demo CLIs and the higher-level REAPER policy helper are currently
at different integration stages, so read
[`docs/REAPER_CENTRAL_CACHE.md`](docs/REAPER_CENTRAL_CACHE.md) before using
central storage in an application.

## GUI model

REAPER's native waveform mipmaps are excellent persistent data, but their zoom
spacing is sparse. `WavePyramid` keeps those native levels and adds
**metadata-only** ratio-4 display levels. Derived extrema are aggregated only
for the visible range or requested tile.

The default tile contains 4096 peaks and is keyed by:

```text
WaveTileKey { level_index, tile_index }
```

Waveform tiles pack max/min codes losslessly into RGBA8. Spectral tiles pack the
existing REAPER 32-bit spectral code directly into RGBA8. This makes the same
cache useful from Qt/PySide6, OpenGL/QRhi, WebGL2, WebGPU, or a CPU renderer.

See [`docs/GUI_WAVEFORM.md`](docs/GUI_WAVEFORM.md).

## Technical background

The byte-exact result comes from reproducing several details that are invisible
at the UI level, including REAPER-style waveform quantization, Cockos WDL FFT
and resampling behavior, spectral phase refinement, a libebur128-style
fourth-order loudness filter, 25 ms loudness energy blocks, REAPER's exact
floating-point update order, and its EOF/mipmap scheduling behavior.

The documentation starts at [`docs/README.md`](docs/README.md). The technical
record is split into:

- [`docs/COMPATIBILITY.md`](docs/COMPATIBILITY.md) — what is proven today and
  what is not;
- [`docs/REVERSE_ENGINEERING.md`](docs/REVERSE_ENGINEERING.md) — recovered
  algorithms and oracle methodology;
- [`docs/REAPER_CENTRAL_CACHE.md`](docs/REAPER_CENTRAL_CACHE.md) — REAPER.ini,
  `GetPeakFileNameEx`, cache maps, and current demo integration status;
- [`docs/GUI_WAVEFORM.md`](docs/GUI_WAVEFORM.md) — tiled waveform/spectral GUI
  data model;
- [`docs/C_ABI.md`](docs/C_ABI.md) — C ABI reference overview;
- [`docs/validation-summary.json`](docs/validation-summary.json) —
  machine-readable validation summary.
